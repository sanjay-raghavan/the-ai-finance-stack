# v0.3 Design Note — Controller Reconciliations Fan-Out

**Status:** Draft. Targets v0.3.
**Author:** Sanjay Raghavan
**Why now:** Controller's reconciliations pass is the first place in the Stack where a single-agent context starts to feel cramped, and where natural parallelism would speed up close. Good first candidate for the sub-agent pattern introduced in `ARCHITECTURE.md`.

---

## The problem

Controller currently runs reconciliations as one sequential pass inside one Claude context. The work breaks down into ~5 independent sub-tasks that don't share much intermediate state:

1. **Bank reconciliations** — one per bank account (BoA operating, BoA payroll, Mercury, etc.)
2. **AR reconciliation** — GL vs. AR subledger vs. open invoices
3. **AP reconciliation** — GL vs. AP subledger vs. open bills
4. **Intercompany reconciliation** — parent's IC receivable vs. sub's IC payable (multi-entity only)
5. **Investment / crypto reconciliations** — custodian balances vs. GL

Each sub-task has its own data source (different MCP, different file, different reconciling-item conventions) and its own reconciling-item language. Today these all share one Claude context, which:

- Blows through the parent's context budget on larger orgs (15+ bank accounts is common at PE-backed companies)
- Forces the parent to swap context as it switches sub-tasks (loses focus, gets less rigorous)
- Runs everything sequentially even though the sub-tasks are independent

## The fix

Controller's reconciliations pass becomes an orchestrator. It spawns one sub-agent per reconciliation, in parallel. Each sub-agent has a tight, focused context and a single deliverable.

```
Controller (reconciliations pass)
    │
    │  spawn (in parallel)
    │
    ├─► sub: bank-rec(BoA operating)        ──► returns ReconResult
    ├─► sub: bank-rec(BoA payroll)          ──► returns ReconResult
    ├─► sub: bank-rec(Mercury)              ──► returns ReconResult
    ├─► sub: ar-rec                         ──► returns ReconResult
    ├─► sub: ap-rec                         ──► returns ReconResult
    ├─► sub: ic-rec(parent <-> sub)         ──► returns ReconResult   (multi-entity only)
    └─► sub: crypto-rec                     ──► returns ReconResult   (crypto pack only)
                                                       │
                                                       ▼
                                  Controller synthesizes into reconciliations.md
                                  Surfaces aggregate exceptions to #finance-alerts
```

## What a sub-agent looks like

Each sub-agent is a one-shot invocation, not a long-lived agent package. It runs in the parent's process via the SDK's `Agent` tool. Spec:

```yaml
# Pseudocode for what Controller sends to the SDK
sub_agent:
  type: bank-reconciliation
  inputs:
    period: 2026-05
    account_name: "BoA — Operating"
    account_gl_number: 1010
    bank_statement_path: ~/finance-data/closes/2026-05/bank-stmts/boa-operating.csv
    prior_recon_path: ~/finance-data/closes/2026-04/reconciliations.md
    materiality_threshold: 1000  # from controller's config.yaml
    customization_refs:
      - customization/reference/chart-of-accounts.xlsx
  tool_access:
    - quickbooks   # read-only
    - Read, Write (sub-folder only)
  output_schema: ReconResult  # see below
  max_context_tokens: 8000
```

## ReconResult schema (shared)

Every sub-agent returns the same shape so Controller can synthesize cleanly:

```yaml
ReconResult:
  account: string                # "BoA — Operating"
  period: string                 # "2026-05"
  gl_balance: number
  source_balance: number         # bank, subledger, custodian
  difference: number             # gl - source
  reconciling_items:
    - description: string
      amount: number
      type: enum                 # timing | error | unrecorded | other
      age_days: number
      severity: enum             # ok | review | escalate
      proposed_action: string    # "Book accrual", "Investigate", "Acceptable timing", etc.
  status: enum                   # tied | minor-diff | needs-review | escalate
  notes: string                  # free-form, anything Controller should know
```

## What Controller does with the results

After all sub-agents return:

1. **Aggregate the ReconResults** — one section per account, sorted by status (escalate → needs-review → minor-diff → tied)
2. **Apply Controller's materiality thresholds** at the aggregate level, not just per-account. Five accounts each off by $4K may be individually below threshold but collectively material.
3. **Write `reconciliations.md`** in the same format as today — sub-agents do *not* write the final doc; the parent does. Keeps the output consistent.
4. **Post to Slack** — Controller's own job, not the sub-agents'. Sub-agents are silent except to the parent.
5. **Surface gaps to `gaps.md`** — anything a sub-agent encountered that should be in `customization/` but wasn't (per the Agent Contract).

## Failure handling

- If a sub-agent fails (timeout, MCP error, malformed inputs), Controller marks that reconciliation as `needs-review — sub-agent failed` and continues with the others. Never fails the whole pass for one sub-agent's problem.
- If more than 50% of sub-agents fail, Controller halts and posts an alert. Something systemic is wrong.
- Sub-agents have no retry logic of their own. If they need a retry, Controller decides whether to re-spawn.

## What this changes for users

- Same artifacts (`reconciliations.md`, Slack updates, audit log) — output format is unchanged
- Faster close on Day 2 (parallel runs cut wall-clock time roughly in half for orgs with 5+ accounts)
- Slightly higher token usage (multiple contexts) — but each context is small, so total cost is roughly flat
- One new config knob in Controller's `config.yaml`:

```yaml
reconciliations:
  parallel_fanout: true          # default v0.3
  max_concurrent_sub_agents: 6   # avoid hammering MCP rate limits
  sub_agent_timeout_seconds: 300
```

Users on v0.2 see no change; opting in is one config flip.

## What this doesn't do

- Doesn't change peer-agent boundaries (Controller still hands off to FP&A via files)
- Doesn't introduce parent/child orchestration (sub-agents are short-lived, one-shot)
- Doesn't apply to passes that are genuinely sequential (close calendar → accruals → reconciliations stays sequential at the *pass* level; only within the reconciliations pass do we fan out)
- Doesn't apply to other agents yet (FP&A's variance decomposition is a likely next candidate; IR's data-pull pass after that)

## Open questions

1. **Sub-agent skill definitions:** does each sub-agent type get its own skill file (`agents/controller/skills/bank-rec-subagent/SKILL.md`, etc.) or do we define them as inline templates in Controller's CLAUDE.md? Lean toward separate files — easier to test independently and reuse for the standalone `bank-recon` agent.
2. **Versioning:** when the sub-agent spec changes, how do we keep Controller and any future user-built sub-agents in sync? Probably a v0.3 `stack:recon-result-schema` shared skill.
3. **Local model vs. API:** can sub-agents use Haiku for cost? Likely yes for bank-rec (mechanical matching); not for ic-rec (judgment-heavy). Per-sub-agent model config.
4. **Audit log granularity:** does each sub-agent get its own audit entry, or just the parent? Probably both — parent logs the orchestration, each sub logs its own work, links via correlation ID.

## Rollout plan

- **v0.3.0:** ship the pattern in Controller's reconciliations pass only, opt-in via config flag, default off
- **v0.3.1:** flip the default to on after a release of soak time
- **v0.4:** extend to FP&A Analyst's variance decomposition and IR's data-pull pass
- **v0.5:** harvest the shared infrastructure (`stack:recon-result-schema`, sub-agent runtime helpers) into reusable patterns documented in `AGENT_PACKAGE_FORMAT.md`
