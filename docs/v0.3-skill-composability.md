# v0.3 Design Note — Skill Composability and Per-Deployer Overrides

**Status:** Draft. Targets v0.3.
**Author:** Sanjay Raghavan
**Why now:** Deployers should be able to customize an agent's behavior — change a threshold, swap a methodology, replace a writing voice — without forking the entire repo. Today the only path is to fork-and-edit, which makes upstream updates painful and discourages adoption.

### Where each agent's behavior is determined

```
agents/<name>/
├── CLAUDE.md                    ← identity + operating doctrine (deployer should rarely change)
├── config.yaml                  ← thresholds, schedule, MCPs (deployer may want to change)
├── skills/                      ← agent-specific methodology (deployer may want to extend or replace)
│   ├── <skill-1>.md
│   └── <skill-2>.md
└── README.md                    ← human-readable (informational; not loaded at runtime)
```

Plus reads from:

```
skills/<shared-skill>.md         ← shared methodology (deployer may want to override per-agent)
customization/                   ← deployer's books, templates, voice (already user-owned)
```

### The composability problem

Today a deployer who wants to do any of the following has to fork the whole repo:

1. **Tighten a threshold.** Controller's `variance_period_over_period_deviation_pct: 25` is too loose for their org; they want 10. They have to edit `agents/controller/config.yaml`. Pulls from upstream now conflict.
2. **Replace a methodology.** FP&A's `variance-decomposition.md` uses Volume × Rate × Mix; their business uses Customer × Product × Channel. They'd need to fork the skill file.
3. **Add a step to a process.** Their close has a unique "approve crypto MTM before posting accruals" step that's not in Controller's calendar. They need to insert a new skill.
4. **Change a writing voice.** IR's exec-summary tone doesn't match their CEO's voice. They want to override it, not delete it.
5. **Add a sub-agent.** Their close needs a custom recon for an obscure subledger. The base agent doesn't know about it.

All five cases are real. None should require a fork.

## The design

A precedence-based override system. Files in `customization/skills/` take precedence over the shipped files of the same name. Same idea as a CSS cascade or a config-overlay system.

### Folder layout (deployer side)

```
customization/
├── org.yaml
├── reference/
├── templates/
├── voice/
└── skills/                          ← NEW in v0.3
    ├── README.md
    ├── <shared-skill>.md            ← override skills/<name>.md (top-level shared)
    │   e.g., variance-decomposition.md, slack-conventions.md
    └── <agent>/
        ├── <skill-name>.md          ← override agents/<agent>/skills/<skill>.md
        │   e.g., controller/close-calendar.md
        └── <new-skill>.md           ← ADD a new skill the base agent doesn't have
            e.g., controller/crypto-mtm-pre-accrual.md
```

### Precedence rules

When an agent loads a skill named `<skill>`:

1. **First check** `customization/skills/<agent>/<skill>.md` — if exists, use this.
2. **Else check** `customization/skills/<skill>.md` (top-level deployer override) — if exists, use this.
3. **Else check** `agents/<agent>/skills/<skill>.md` (shipped agent-specific) — if exists, use this.
4. **Else check** `skills/<skill>.md` (shipped shared) — if exists, use this.
5. **Else** report a "skill not found" error.

This is the order from most-specific to least-specific. A deployer who copies a shipped skill into `customization/skills/<agent>/<skill>.md` and edits it is now running their version, not ours, and our upstream changes don't conflict.

### Adding new skills

`customization/skills/<agent>/<new-skill>.md` is automatically discovered by the agent at load time and added to its available skill list. No need to edit the agent's `config.yaml`. Agents enumerate their own skill directory plus the customization overlay.

### Removing a shipped skill

If a deployer wants to *disable* a shipped skill rather than replace it, they create an empty stub at the override path with a `disabled: true` frontmatter flag:

```markdown
---
disabled: true
reason: "Our org doesn't do this — we handle it manually in NetSuite"
---
```

The agent loads the stub, sees `disabled: true`, and treats the skill as if it doesn't exist.

### Customizing config values without overriding the whole skill

For simple value changes (a threshold, a cadence), deployers shouldn't need to copy a whole skill file. Instead, agent `config.yaml` keys can be overridden in:

```
customization/config/<agent>.yaml
```

Same precedence: customization overrides ship. The runtime merges (deep merge) the two files at load.

Example — tighten Controller's variance threshold without copying any skill files:

```yaml
# customization/config/controller.yaml
thresholds:
  accrual_period_over_period_deviation_pct: 10   # was 25 in shipped config
```

### Sub-agents (when v0.3 fan-out lands)

Sub-agents inherit the same precedence model. A deployer can:

- Override the schema each sub-agent returns
- Add a brand-new sub-agent type
- Disable a sub-agent shipped in the base

Each sub-agent type has its own skill file under `agents/<parent>/skills/sub-agents/<type>.md`; deployer overrides land in `customization/skills/<parent>/sub-agents/<type>.md`.

## What this changes about authoring agents

Agent authors (us, plus contributors) get one new responsibility: **mark skills as "deployer-overridable" or "not."**

```yaml
# Frontmatter in any shipped skill
---
name: variance-decomposition
overridable: true               # deployer can replace or extend
override_guidance: |
  Most deployers won't need to. If you change the methodology, ensure
  your replacement produces an output that downstream skills (fpa-analyst's
  scenario-flex, IR's exec-summary) can still consume — they expect a
  `driver_breakdown` block with `volume`, `rate`, `mix`, and `headcount`
  fields. Replacements that change that schema may break downstream.
---
```

Some skills should NOT be overridable (the proposal-format schema, the approval-record-format, the 8-check validation). For those:

```yaml
---
name: proposal-format
overridable: false              # contract; do not override
why: |
  This is the canonical schema 8 agents agree to. Overriding it locally
  breaks the integration. If you need different fields, propose an
  upstream change.
---
```

If a deployer tries to override a `overridable: false` skill, the runtime emits a hard warning at startup but doesn't block (deployer's choice; their books).

## Rollout plan

- **v0.3.0 alpha:** ship the precedence loader. Deployers can override top-level shared skills only. Per-agent overrides come next.
- **v0.3.0 beta:** ship per-agent overrides (`customization/skills/<agent>/<skill>.md`).
- **v0.3.0:** ship config-value overrides (`customization/config/<agent>.yaml`).
- **v0.3.1:** ship the `overridable:` frontmatter convention; audit every shipped skill and mark.
- **v0.4:** ship sub-agent override support (depends on the sub-agent infrastructure landing first per `v0.3-controller-fanout.md`).
- **v0.5:** ship a `customize-skill` interactive tool that walks the deployer through forking a shipped skill, dropping it in `customization/skills/`, and showing the diff. Lowers friction.

## What this preserves

- **Upstream updates stay clean.** Deployer's changes live in `customization/`, which is gitignored. `git pull` on the Stack repo never conflicts with their customizations.
- **The 8-check validation contract.** The non-overridable skills (proposal-format, approval-record-format, approval-policy) stay canonical, so QBO Poster's safety checks keep working.
- **Discoverability.** Deployers can `ls customization/skills/` and see exactly what they've overridden. No hidden state.
- **Curriculum value.** The lesson series can still teach "here's how Controller works" against the shipped skills, and "here's how to customize it for your org" as a separate lesson — without the latter requiring readers to learn git fork-and-rebase.

## Open questions

1. **What about CLAUDE.md overrides?** Today CLAUDE.md is the identity doc. Deployers shouldn't fork it casually (you'd lose upstream improvements to the agent's reasoning). But some orgs may want to add a "you also know about our specific tooling" preamble. Probably handled via a `customization/agents/<agent>/preamble.md` that the runtime concatenates onto CLAUDE.md at load.
2. **Versioning.** When the shipped skill changes upstream but the deployer's override doesn't, how does the deployer find out their override is stale? Possibly a `min_compatible_shipped_version: "0.3.0"` field they bump when they vet their version.
3. **Skill-skill dependencies.** If Skill A is overridden, do Skills B and C that depended on its output break? Need a dependency-graph in `config.yaml` and a runtime sanity check.
4. **Testing.** Encourage deployers to test their overrides against the same fixtures we use for the shipped versions. Provide a `pytest` harness that takes both the shipped and overridden versions through the same inputs.
